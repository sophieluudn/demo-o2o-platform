# 權限原則與實作狀態

更新日期：2026-10-20

## 已確認的規則

- 登入 Email 對應唯一使用者，去除首尾空白並忽略大小寫；不存在、停用、重複或沒有有效指派時拒絕登入。
- 一般使用者即使被指派 A、B，選 A 後只看 A，下拉只有 A；切換 B 後依 B 的角色判斷，不把 A 的操作權限套用到 B。這是使用者釐清後的最終規則，取代合併顯示 A、B 專案的建議。
- 有效指派要求單位啟用、角色啟用且與單位匹配。同一單位只允許一個角色；舊重複指派不合併授權，需修正資料。
- 內建系統管理員依角色 ID 1 識別，只可指派「全部單位」（`*`），與所有個別指派互斥；一般角色只可屬於個別單位。系統管理員可進入任一啟用單位，列表預設該單位並可改篩選全部。
- 功能包含專案列表、會員使用紀錄、登入與註冊統計、使用者、角色及單位管理，分別設定檢視、編輯或匯出／匯出紀錄。
- 選單、列表、直接網址、按鈕、儲存及匯出均檢查權限；匯出紀錄依使用者、專案、報表分開，登出清除。
- 使用者管理的編輯權允許修改可見使用者的姓名、Email、整體狀態及其他單位指派；不限制權限層級，預期由開發部門使用。
- 「管理專案」改稱「單位與角色」，停用項目不供新增指派。不提供角色刪除。
- 內建管理員角色可改名稱與說明，固定全部單位、啟用及完整權限，不可停用、刪除或縮減權限。畫面限制與儲存判斷皆生效。
- 全域管理員使用者列不受個別單位篩選排除，單位顯示「全部單位」，角色顯示內建角色目前名稱。有使用者管理權者可見該列；停用該使用者需確認「使用者為系統管理員，確定要停用?」，確認後重查權限與最後一位管理員保護才儲存。停用使用者不會停用內建角色。
- 角色列表在任一單位篩選下保留內建管理員角色，所屬顯示全部單位；有角色檢視權即可看見，不因顯示而增加編輯權限。其他角色仍受單位範圍限制。
- 單位新增、編輯及停用依角色的單位管理權限。單位名稱忽略英文大小寫檢查重複；更名同步專案、使用者、角色及指派。
- 新增專案固定歸屬登入後選擇的單位，儲存時再次檢查建立權限。
- 登入及既有 session 在重新整理、路由切換、操作與跨分頁資料更新時重查。使用者停用或全部指派失效即登出；目前單位失效而仍有其他有效單位時返回選單。
- 同頁儲存後立即依新狀態重新導向。撤銷目前單位時關閉編輯視窗並清除目前專案、報表及匯出紀錄，避免留在無權限頁面。
- 單位管理資格獨立於業務功能：使用者與管理角色仍啟用、匹配且有相應權限，即使該單位停用，也可在管理列表檢視或重新啟用。此資格不開放該單位業務功能，且仍需有另一個有效單位才能登入。
- Email 只做基本格式、首尾空白及不分英文大小寫的唯一性檢查，不處理 Gmail 點號或加號別名。

## 資料相容

保留 `o2o-projects` 與 `o2o-system`。使用者指派存在 `assignments[]`，舊欄位保留第一組值；明確空陣列不補回授權。舊內建管理員個別指派轉為唯一一組 `*`＋角色 1，角色也固定到 `*`，保留使用者、角色等其他欄位與所有其他資料。一般角色若仍是 `*`，保留原資料並標示失效，不參與授權，由有權者修正。

舊專案、角色與指派仍依單位名稱關聯，更名同步全部相關資料；選擇單位以 `unitId` 記錄在分頁 session。最後一位啟用管理員的保護以有效的全域內建角色指派判斷。

## 正式服務尚需完成

登入頁只保留標題與登入按鈕，預設採使用者 ID 1 的 Email 模擬身分，測試可用 sessionStorage 的 `o2o-demo-login-email` 指定帳號。沒有 Google OAuth、後端身分驗證或授權 API，不能證明帳號持有權。正式部署需由伺服器驗證 Google 身分，對應固定識別與唯一 Email，並對每個讀寫／匯出 API 執行授權。

localStorage 可由瀏覽器使用者修改，不提供安全隔離；跨兩個儲存鍵也不具資料庫交易保證。正式服務應採固定單位 ID、唯一約束及交易同步資料。

## 驗證

`scripts/verify-access.mjs` 涵蓋上述規則：指派選項與互斥、繞過 UI 的儲存驗證、內建角色不變條件、最後管理員保護、單位隔離、跨單位不同角色、部分／全部停用、同頁及跨分頁撤權、非管理員重新啟用單位、篩選全部仍維持新增歸屬、舊資料遷移、Email 唯一、單位更名與網址／匯出權限。
