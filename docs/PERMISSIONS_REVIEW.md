# 權限原則與系統管理 review

日期：2026-10-20

## 結論

「使用者看到所有被授權單位建立的專案」原則合理。授權應以每組「使用者 × 單位 × 角色」判斷，再合併可見專案；不能只使用第一組設定，也不能將甲單位的操作權限套用到乙單位。

目前程式已支援多組 `assignments` 的儲存、列表顯示、單位搜尋及管理員保護，但尚未將這些設定用於專案存取。Review 後依使用者補充，已實作各單位獨立角色、同一使用者每單位一個角色及單位／角色連動；其餘尚未完成的授權限制仍列於下表。

## 優先修正的衝突與缺口

| 優先 | 發現與程式依據 | 影響及建議 |
| --- | --- | --- |
| 高 | `demoSession` 只有 `authenticated`；`demo-login` 沒有綁定使用者 | 無法知道目前應套用哪個人的 `assignments`。Demo 需對應選定的使用者 ID；正式登入應對應唯一身分識別，而不是只記錄已登入。 |
| 高 | `filteredProjects()` 只有搜尋與手動單位篩選；`render()` 只驗證已登入，並直接依 ID 取得專案 | 目前能看到所有專案，也可直接開啟其他單位的編輯、會員紀錄、統計網址。需要共用存取判斷，涵蓋列表、單位選項、總筆數、網址、複製、QR、儲存及匯出；不能只隱藏列表列。 |
| 高 | `permissionMenus()`／`roleForm()` 儲存功能權限；`systemNavigation()`／`systemPage()` 沒有使用角色權限決定存取 | 使用者、角色與單位管理目前皆未限制管理範圍；有入口不代表有權限，隱藏入口也不代表不能直接進入。應同時檢查功能權限及資料所屬單位。 |
| 已修正 | 角色與單位的對應 | 已確認各單位角色獨立，角色下拉只列出該單位角色，更換單位會清除原角色；儲存時檢查對應關係。已被指派的角色不能直接移到其他單位。 |
| 高 | 專案 `unit`、角色 `unit`、`assignments[].unit` 都存單位名稱；單位改名僅更新使用者與角色 | 專案仍保留舊名稱，若直接依名稱檢查權限，單位改名後可能看不到原專案。應改以不變的 `unitId` 關聯專案、角色及指派；名稱僅供顯示。舊資料要明確對照及處理無法辨識的項目，不能為了遷移就自動增加授權。 |
| 高 | 狀態可設定，但登入未檢查使用者狀態；專案存取未檢查角色／單位狀態 | 停用目前多為資料標記。建議停用使用者使整體登入失效；停用某角色或單位，僅使相關指派失效，不影響其他有效單位。 |
| 已修正 | 角色名稱唯一性的範圍 | 不同單位可各自建立同名角色，功能權限獨立儲存；角色名稱只在同一單位內檢查重複。未來仍須將名稱關聯改為固定單位 ID。 |
| 已修正 | 同一使用者的單位指派 | 同一單位只能指定一個角色；新增及編輯儲存時均拒絕重複單位，即使兩列角色不同。舊衝突資料不自動合併授權，需在編輯時修正。 |
| 中 | 使用者 Email 格式有驗證，但沒有唯一性；登入也沒有實際身分關聯 | 同一人可能重複建立，造成跨單位權限分散。正式以身分提供者的固定 ID 關聯；Demo 至少應避免同一 Email 重複建立，新增既有身分的單位授權應更新同一人。 |
| 中 | `saveProject()` 新增時使用第一個單位，沒有讓建立者選擇其被授權的單位 | 跨單位主管建立專案時，可能歸到錯誤或未授權單位。新增應選擇有建立權限的單位，儲存時再次驗證；編輯不可藉修改歸屬跨越權限。 |
| 中 | 權限鍵 `projects` 對應的是 `#system/projects` 的單位管理；真正專案列表的權限鍵是 `project-list` | 「專案編輯」舊角色的 `projects` 值實際代表單位管理，容易誤解或給錯權限。建議使用明確的功能鍵，如 `projects.read`、`projects.write`、`units.manage`，並制定舊鍵遷移對照，勿自行把舊鍵轉成更多權限。 |

## 建議的授權規則

1. 登入對應單一啟用使用者，查詢該使用者全部指派。
2. 每組指派需有存在且啟用的單位、存在且啟用的角色，且角色所屬單位符合該指派。
3. 在該單位具有專案檢視權限，才納入該單位的專案。多個單位的結果取聯集，同一專案只列一次。
4. 先套用授權，再做搜尋、單位篩選、計數、分頁與匯出。「全部單位」代表全部被授權單位，不是全平台。
5. 編輯、新增、匯出、會員紀錄等操作，只使用該使用者在專案所屬單位的唯一角色判斷功能權限，其他單位的角色不參與。同一單位不得設定多個角色，也不做角色權限聯集。
6. 專案所屬單位與「由誰建立」分開記錄。建立者離職或權限改變，不會讓專案失去所屬單位。

例如：

| 使用者 | 指派單位 | 該單位角色權限 | 可見與可操作結果 |
| --- | --- | --- | --- |
| 陳查理 | 行動發展部 | 檢視、編輯專案 | 看見該單位專案並可編輯 |
| 陳查理 | 娛樂生活事業部 | 僅檢視專案 | 看見該單位專案，不能因另一單位的角色而取得編輯權 |
| 陳查理 | 未被指派的第三單位 | 無 | 不出現在列表、篩選選項及總筆數；直接網址也應拒絕 |

## 系統管理需要補定的界線

- **系統管理員是否跨單位：** 目前角色 ID 1 被視為內建管理員，尚未定義是否能略過單位範圍。依此次原則，建議預設仍需明確的單位指派；若需要平台級管理員，應另設明確的全平台範圍，不可僅因角色名稱含「管理員」就放行。
- **管理使用者：** 單位主管只能增減自己可管理單位的指派，不可刪改同一使用者的其他單位設定。姓名及 Email 為全域身分資料，建議由平台管理員維護，避免甲單位主管影響乙單位使用者身分。
- **管理角色：** 只能管理有授權的單位角色，且不能授予超過自己可授予的功能，更不能自行取得平台管理員權限。
- **管理單位：** 新增、停用單位會影響整個組織；建議保留給平台管理員。單位主管可以管理現有單位到什麼程度，應單獨決定。
- **專案停用：** 與單位／角色停用不同。建議有管理權的使用者仍能看到所屬單位的停用專案，以便重新啟用；活動對外開放狀態另行處理。
- **欄位命名：** 使用者彈窗的「管理專案」實際設定單位及角色，建議未來改為「管理單位與角色」，避免誤以為是逐一指派專案。

## 建議資料模型與遷移順序

```text
users: id, identityId, name, email, enabled
units: id, name, enabled
roles: id, unitId, name, description, enabled, permissions[]
assignments: userId, unitId, roleId
projects: id, unitId, createdBy, ...
```

目前內嵌在 `users[].assignments` 的陣列可繼續使用，不一定要拆成獨立儲存；重點是關聯欄位改用 ID，以及所有判斷都讀取完整陣列。舊 `user.unit`／`user.role` 僅作相容資料，不得用來判斷完整授權。

建議依序：綁定登入使用者 → 明確處理單位 ID 遷移 → 角色／單位連動與狀態檢查 → 共用授權判斷 → 專案及系統管理操作套用授權 → 驗證篩選、分頁、匯出及直接網址。

## 本次已完成

- 移除選單管理入口、頁面處理、排序／顯示設定及功能權限選項。
- 系統管理固定為使用者管理、角色管理、單位管理；舊 `#system/menus` 不再提供管理頁，會返回使用者管理。
- 讀取舊資料時，清除 `menus` 設定及角色的 `menus` 權限，不重設既有使用者、角色、單位與跨單位指派。
- 依補充原則，實作單位內角色名稱唯一、跨單位同名角色獨立、單位／角色下拉連動及儲存驗證，以及每個使用者每單位只能有一個角色的檢查。

目前仍是 localStorage／sessionStorage 的純前端 Demo。未來若接正式服務，存取判斷必須由後端依登入身分執行；瀏覽器內的設定與檢查只能用於示範流程。
